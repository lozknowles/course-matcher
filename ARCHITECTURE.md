# Architecture — Course Match

This document describes the technical design of the Course Match prototype so that a support or development team can understand the system without prior project context.

> **Scope:** this is the architecture of the current independent demonstration, not a prescribed Lincoln College production architecture.

## 1. Architectural goals

The prototype was designed around six goals:

1. **Keep student-result processing local to the browser where practical.**
2. **Separate course data from matching logic.**
3. **Make every machine-evaluated requirement explainable.**
4. **Require human verification before matching OCR-derived data.**
5. **Fail toward manual handling rather than fabricate certainty.**
6. **Remain deployable as static files with very little infrastructure.**

## 2. System context

```text
┌───────────────────────────────┐
│ Student / tutor / adviser     │
│ Browser                       │
└──────────────┬────────────────┘
               │
               │ HTTPS static files
               ▼
┌───────────────────────────────┐
│ Static web host               │
│                               │
│ index.html                    │
│ styles.css                    │
│ app.js                        │
│ document-core.js              │
│ matcher-core.js               │
│ courses.js                    │
│ vendor/                       │
└───────────────────────────────┘

               ▼
┌───────────────────────────────┐

```

There is no application backend, database, queue, session service or results API in the current repository.

## 3. Runtime components

### `index.html`

Responsibilities:

- static application shell;
- accessibility landmarks and labels;
- student workflow panels;
- adviser workflow panel;
- disclaimer/about content;
- loading `app.js` as an ES module.

It contains no course-matching business logic.

### `styles.css`

Responsibilities:

- responsive visual layout;
- status presentation for green/amber/red results;
- form/table presentation;
- mobile behaviour.

It should not become a source of business state or eligibility logic.

### `app.js`

`app.js` is the browser controller/orchestration layer.

Responsibilities:

- managing transient browser state;
- switching student/adviser/about views;
- manual grade-entry UI;
- reading text/CSV files;
- invoking PDF.js for PDF extraction;
- invoking Tesseract.js for image OCR;
- enforcing the verification step in the UI flow;
- collecting interests/career text;
- calling the pure matching functions;
- rendering matching evidence;
- parsing adviser CSV data and rendering reverse matches.

It imports data from `courses.js` and logic from `matcher-core.js`.

It should not become the canonical source of course requirements.

### `document-core.js`

Responsibilities:

- reconstructing PDF.js text items into visual rows rather than flattening tables;
- visiting every PDF page in order;
- releasing each PDF page after extraction.

### `matcher-core.js`

This is the domain/matching layer and is deliberately independent of the DOM.

Responsibilities:

- subject-name normalisation;
- grade parsing;
- Combined Science pair handling;
- qualification counting;
- individual course-rule evaluation;
- green/amber/red indicative classification;
- interest-aware course ranking;
- simple OCR-style results-text parsing.

Because it has no browser dependencies, it can be exercised directly with Node tests.

### `courses.js`

This is the current catalogue/data layer.

Responsibilities:

- subject-area list;
- encoded course records;
- source URLs;
- date checked;
- human-readable summaries;
- machine-readable grade rules;
- non-grade warnings;
- interest cross-listing and keywords;
- official subject-area links.

For a College-supported implementation, this file (or its successor data source) needs clear business ownership and an approved update process.

### `vendor/`

Generated browser runtime dependencies:

- Tesseract.js browser bundle;
- Tesseract worker/core files;
- English OCR language data;
- PDF.js module and worker.

`vendor/` is generated by `scripts/vendor.mjs` and is not canonical hand-maintained source.

The vendor build verifies that compressed English language data can be decompressed and is plausibly sized. Corrupt/truncated OCR data fails preparation instead of reaching browsers.

### `tests/matcher.test.mjs`

Regression tests for the domain rules.

The tests are particularly important because a seemingly small change to qualification counting or a course rule can affect student-facing recommendations.

## 4. Student data flow

### Manual entry

```text
manual subject + grade rows
        ↓
verification table
        ↓
state.grades
        ↓
matcher-core.normaliseGrades()
        ↓
matchCourse()/rankCourses()
        ↓
rendered evidence
```

### Image/screenshot OCR

```text
image File object
      ↓
app.js processFile()
      ↓
ocrImage()
      ↓
Tesseract.js worker in browser
      ↓
plain extracted text
      ↓
parseResultsText()
      ↓
editable/manual grade rows
      ↓
MANDATORY verification screen
      ↓
matching
```

### PDF

```text
PDF File object
      ↓
PDF.js getDocument()
      ↓
for every page:
  ├─ text layer present → extract text
  └─ no usable results / sparse mixed page → render page to canvas → Tesseract OCR
      ↓
parseResultsText()
      ↓
verification
      ↓
matching
```

PDF text items are grouped into visual rows before parsing. A single Tesseract worker is reused for every page that requires OCR, and successful extraction proceeds directly to mandatory human verification.

## 5. Browser state

The current state object is intentionally small:

```js
{
  grades: [],
  interests: new Set(),
  cohort: []
}
```

It is in memory only.

There is no localStorage/sessionStorage persistence and no backend persistence of entered results in the current code.

Refreshing or closing the page loses the state.

## 6. Qualification model

Raw input rows have this shape:

```js
{
  subject: 'Mathematics',
  grade: '5'
}
```

After normalisation a grade is represented as one of:

```js
{ type: 'single', value: 5, raw: '5' }
```

```js
{ type: 'pair', values: [5, 5], raw: '5-5' }
```

```js
{ type: 'text', raw: '...' }
```

Legacy letter grades are mapped conservatively to approximate numeric values by `parseGrade()` and marked with `converted: true`.

## 7. Combined Science handling

Combined Science is the main qualification-counting special case in the prototype.

A pair such as:

```text
5-5
```

is treated as two qualification outcomes when counting GCSEs at a threshold.

A single:

```text
5
```

is treated as one evidenced result.

This is intentional. The matcher must not infer a second GCSE unless the input actually evidences a double award.

When a single Combined Science grade may materially affect a rule, the result contains a warning telling the user to check whether a pair should have been entered.

## 8. Course rule schema

A course record contains metadata and a `rule` object.

Example:

```js
{
  id: 'computing-l3',
  title: 'Level 3 Computing and Information Technology',
  subject: 'Computing',
  level: 3,
  campus: 'Lincoln Campus',
  url: 'https://...',
  checked: '2026-08-24',
  summary: '...',
  rule: {
    minTotal: { count: 5, grade: 4 },
    subjects: [
      { subject: 'Mathematics', grade: 5 },
      { subject: 'English Language', grade: 4 }
    ]
  },
  warnings: ['...'],
  keywords: ['coding', 'cyber']
}
```

### Supported rule primitives

#### `minTotal`

```js
minTotal: { count: 5, grade: 4 }
```

Means at least five evidenced qualifications at grade 4 or above.

#### `subjects`

```js
subjects: [
  { subject: 'Mathematics', grade: 5 },
  { subject: 'English Language', grade: 4 }
]
```

Every listed subject requirement must be evidenced.

#### `anySubjects`

```js
anySubjects: [
  {
    subjects: ['Combined Science', 'Physics', 'Chemistry', 'Biology'],
    grade: 4
  }
]
```

At least one subject from the group must meet the threshold.

#### `noFormalGrades`

```js
noFormalGrades: true
```

Signals that there is no formal GCSE rule encoded. Other human checks may still apply.

#### `manualOnly`

```js
manualOnly: true
```

Forces an amber/manual-check outcome because the published requirement cannot safely be reduced to the current numeric rule model.

### Fields that affect ranking rather than eligibility

`interests` can cross-list a course into another subject family.

`keywords` can contribute to free-text career/topic relevance.

Neither should be used to bypass eligibility checks.

## 9. Matching algorithm

`matchCourse()` performs these stages:

1. normalise the supplied qualifications;
2. evaluate all hard encoded rule primitives;
3. collect evidence rows for the UI;
4. calculate hard failures and an approximate `gaps` measure;
5. append Combined Science ambiguity warning if applicable;
6. classify the result;
7. calculate an internal ranking score.

Current status model:

- **green** — all encoded hard rules pass;
- **amber** — rule failures are relatively close or the course is explicitly manual-only;
- **red** — larger encoded grade gaps.

These colours are **indicative UI bands, not admissions outcomes**.

The `score` is only a ranking mechanism inside the prototype. It is not a probability of acceptance and should never be presented as one.

## 10. Interest ranking

`rankCourses()` first evaluates eligibility, then adds relevance based on:

- selected subject interests;
- cross-listed `course.interests`;
- optional career/topic text matching the title, subject or keywords.

If the student selects one or more interests, courses outside those subject families are filtered out.

This means the system answers roughly:

> “Within the things this student says they are interested in, which encoded courses appear most worth discussing?”

It does not attempt to infer interests from grades.

## 11. Adviser reverse matching

The adviser workflow uses exactly the same `matchCourse()` function as the student workflow.

```text
selected course
      +
anonymised cohort rows
      ↓
matchCourse(person.grades, selectedCourse)
      ↓
sort by internal score
      ↓
show candidate + evidence
```

This reuse is important: there should not be separate hidden eligibility logic for student and adviser views.

## 12. CSV parser

The adviser CSV reader is intentionally lightweight and supports quoted fields/doubled quotes.

Expected shape:

```csv
id,interest,Mathematics,English Language,Combined Science
S-001,Computing,5,4,5-5
```

All columns other than `id` and `interest` are interpreted as qualification names.

For a production College integration, use an approved structured data contract rather than treating arbitrary CSV as a permanent integration API.

## 13. Privacy and security boundary

### Current positive properties

- no application results backend;
- no database;
- no deliberate upload of student documents to an OCR provider;
- locally vendored OCR/PDF libraries;
- transient in-memory student state;
- output escaping for user-controlled values inserted into HTML in sensitive rendering paths;
- no runtime course scraping.

### What this does not prove

The prototype has not, by virtue of these properties alone, established:

- College security accreditation;
- a completed DPIA;
- penetration-test assurance;
- accessibility compliance;
- records-retention compliance;
- production dependency-management processes;
- an approved authentication/authorisation model.

These are governance/productionisation activities, not assumptions.

## 14. Trust boundaries

```text
UNTRUSTED / USER-CONTROLLED
- uploaded image/PDF/text/CSV
- manually entered grade values
- adviser CSV IDs/interests

TRUSTED APPLICATION SOURCE
- matcher-core.js
- reviewed courses.js snapshot
- application static code

EXTERNAL REFERENCE
- official Lincoln College links
```

OCR output is explicitly treated as untrusted until a person verifies it.

## 15. Error/failure behaviour

### OCR unavailable

If Tesseract runtime files are missing or OCR fails, the UI reports the failure and manual entry remains available.

### PDF.js unavailable

The PDF path reports that the local PDF vendor bundle is missing. Manual entry remains available.

### OCR cannot recognise grades

The parser reports no recognised pairs and directs the user to manual entry/verification.

### Incomplete qualification evidence

The matcher does not fill in missing grades. Missing required evidence causes failed checks/amber or red outcomes.

### Unencoded course

No eligibility is fabricated; only an official subject link is shown.

## 16. Build and dependency architecture

There is no application compilation/bundling stage.

The only preparation step is runtime dependency vendoring:

```text
package.json pinned dependencies
             ↓
          npm install
             ↓
      scripts/vendor.mjs
             ↓
          vendor/
             ↓
        static hosting
```

This was chosen so the browser can load OCR/PDF dependencies locally rather than from a CDN.

## 17. CI

The GitHub Actions workflow performs:

```text
checkout
  ↓
Node 22
  ↓
npm install
  ↓
npm test
  ↓
npm run vendor
```

The important invariant is that both the matching tests and the reproducibility of the local vendor bundle are exercised.

A future production pipeline should add whatever linting, accessibility, SAST/dependency and deployment controls CIS standardises on.

## 18. Current demo deployment

The existing `scripts/deploy-production.sh` is deliberately environment-specific.

It:

1. requires a clean `main` checkout;
2. installs dependencies and runs tests;
3. generates vendor assets;
4. uploads to an SSH-user-owned staging directory;
5. backs up the existing demo folder;
6. uses `sudo` for the final document-root sync;
7. verifies the live application and vendor files.

This mechanism is **not part of the domain architecture**. A College deployment could use any appropriate static hosting/CDN/web platform.

## 19. Change impact guide

### Change visual appearance

Primary files:

- `styles.css`
- `index.html`

Risk: accessibility/responsive regressions.

### Change interaction flow

Primary file:

- `app.js`

Risk: verification gate or state-flow regression.

### Change grade interpretation/matching

Primary file:

- `matcher-core.js`

Required: regression tests.

Risk: affects every encoded course and both student/adviser modes.

### Change a course requirement

Primary file:

- `courses.js`

Required:

- verify source;
- distinguish mandatory from advisory wording;
- update `checked` date;
- add/update tests;
- update changelog.

### Add a new rule type

Primary files:

- `matcher-core.js`
- `courses.js`
- tests
- this architecture document.

Do not encode a new field in `courses.js` unless the matcher explicitly supports and tests it.

## 20. Productionisation options

If Lincoln College chooses to develop the concept further, the cleanest path is likely to retain the separation already present:

```text
Presentation/UI
      ↓
Qualification + matching service/domain library
      ↓
Authoritative, versioned curriculum rules
```

The current static files could evolve in several ways without discarding the core design:

- front end can be replaced with the College standard stack;
- matcher can become a shared TypeScript library/service;
- `courses.js` can become an approved versioned data feed/database;
- identity can be added around adviser features;
- audit can record decisions/rule versions without retaining uploaded documents;
- integrations can consume structured results from approved College systems.

The most important architectural property to preserve is that **course requirements and matching decisions remain explicit, versioned, reviewable and explainable**.

## 21. Things deliberately not in the prototype

- automated offers;
- enrolment decisions;
- student identity lookup;
- user accounts;
- server-side document storage;
- analytics on student grades;
- automatic course-page scraping into live decisions;
- opaque AI/LLM judgement of suitability;
- a hidden weighted admissions model.

Those omissions are intentional safeguards as much as they are prototype simplifications.

## 22. Support principle

When uncertain, prefer this order:

1. preserve the student's original evidence;
2. require a human to verify extracted data;
3. show what the encoded rule actually checked;
4. link to the authoritative current course information;
5. escalate judgement to the appropriate College person.

The software should make that process easier, not replace it.
